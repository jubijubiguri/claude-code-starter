# CLAUDE.md

LLM이 코딩 과정에서 흔히 저지르는 실수를 줄이기 위한 행동 지침입니다. 필요에 따라 프로젝트별 지침과 함께 사용하세요.

**트레이드오프:** 이 지침은 속도보다는 신중함을 우선하도록 설계되어 있습니다. 단순한 작업에서는 상황에 맞게 판단하세요.

## 1. 코딩하기 전에 생각하기

**추측하지 마세요. 혼란을 숨기지 마세요. 트레이드오프를 명확히 드러내세요.**

구현하기 전에:

* 가정을 명확하게 밝히세요. 확실하지 않다면 질문하세요.
* 여러 가지 해석이 가능하다면 임의로 하나를 선택하지 말고 각각 제시하세요.
* 더 단순한 접근법이 있다면 알려주세요. 필요하다면 사용자의 요청에 이견을 제시해도 됩니다.
* 불분명한 부분이 있다면 작업을 멈추세요. 무엇이 헷갈리는지 명확하게 설명하고 질문하세요.

## 2. 단순함을 최우선으로

**문제를 해결하는 데 필요한 최소한의 코드만 작성하세요. 추측성 기능은 추가하지 마세요.**

* 요청받지 않은 기능을 추가하지 마세요.
* 한 번만 사용되는 코드를 위해 불필요한 추상화를 만들지 마세요.
* 요청하지 않은 "유연성"이나 "설정 가능성"을 추가하지 마세요.
* 실제로 발생할 수 없는 상황을 위한 에러 처리를 만들지 마세요.
* 50줄이면 해결할 수 있는 코드를 200줄로 작성했다면 다시 단순하게 작성하세요.

스스로에게 물어보세요:
"시니어 엔지니어가 이 코드를 보고 지나치게 복잡하다고 말할까?"
그렇다면 더 단순하게 만드세요.

## 3. 필요한 부분만 정확하게 수정하기

**반드시 필요한 부분만 건드리세요. 본인이 만든 변경으로 인해 생긴 문제만 정리하세요.**

기존 코드를 수정할 때:

* 주변 코드, 주석, 포맷을 임의로 "개선"하지 마세요.
* 문제가 없는 부분을 리팩터링하지 마세요.
* 본인이 다른 방식을 선호하더라도 기존 코드 스타일을 따르세요.
* 관련 없는 데드 코드를 발견했다면 언급만 하고 삭제하지 마세요.

변경 사항으로 인해 불필요한 코드가 생겼다면:

* 본인의 변경으로 인해 사용되지 않게 된 import, 변수, 함수는 제거하세요.
* 기존부터 존재하던 데드 코드는 별도 요청이 없다면 제거하지 마세요.

판단 기준: 변경된 모든 줄은 사용자의 요청과 직접적인 연관성이 있어야 합니다.

## 4. 목표 중심으로 실행하기

**성공 조건을 정의하고, 검증될 때까지 반복하세요.**

작업을 검증 가능한 목표로 바꾸세요:

* "유효성 검사 추가" → "잘못된 입력에 대한 테스트를 작성한 뒤, 해당 테스트가 통과하도록 구현"
* "버그 수정" → "버그를 재현하는 테스트를 작성한 뒤, 해당 테스트가 통과하도록 수정"
* "X 리팩터링" → "리팩터링 전후 모두 테스트가 통과하는지 확인"

여러 단계로 이루어진 작업이라면 간단한 계획을 먼저 제시하세요:

```text
1. [작업] → 검증: [확인 방법]
2. [작업] → 검증: [확인 방법]
3. [작업] → 검증: [확인 방법]
```

명확한 성공 조건이 있으면 독립적으로 검증하며 작업을 반복할 수 있습니다.
반대로 "작동하게 만들기"처럼 모호한 성공 조건은 작업 중 계속해서 추가 확인을 필요로 합니다.
