# 1장. 공통 CLAUDE.md — Claude에게 "일 잘하는 법"을 가르치는 파일

> **바쁘신 분을 위한 3줄 요약**
>
> 1. `CLAUDE.md`는 Claude가 **작업 시작 때마다 자동으로 읽는 업무 지침서**입니다.
> 2. AI 대가 카파시가 관찰한 **"AI의 흔한 코딩 실수"를 막는 4가지 원칙**이 담겨 있습니다.
> 3. **셋업 스크립트가 자동으로 설치**하므로, 직접 하실 일은 없습니다.

먼저 소개할 것은 **CLAUDE.md**라는 파일 하나입니다. 파일 하나가 뭐 그리 중요할까 싶으실 수 있는데, 이 파일이 있고 없고에 따라 Claude가 일하는 방식이 눈에 띄게 달라집니다.

## CLAUDE.md가 뭔가요?

새로운 팀원이 입사하면 우리는 업무 가이드 문서를 건네줍니다. "우리 팀은 이런 방식으로 일해요", "이런 건 꼭 지켜주세요" 같은 내용이 담겨 있죠. 덕분에 새 팀원에게 같은 설명을 매번 반복하지 않아도 됩니다.

**CLAUDE.md는 Claude에게 건네주는 업무 가이드 문서입니다.**

Claude Code는 작업을 시작할 때마다 이 파일을 자동으로 읽고, 여기 적힌 지침을 따릅니다. 이 파일이 없으면 어떻게 될까요? Claude에게 매번 "간단하게 만들어줘", "요청한 것만 수정해줘" 같은 말을 반복해야 합니다. **한 번 적어두면 매번 말할 필요가 없어지는 것**, 그게 CLAUDE.md의 역할입니다.

## 이 파일은 어디서 나온 건가요?

**Andrej Karpathy(안드레 카파시)**라는 분이 있습니다. OpenAI(ChatGPT를 만든 회사)의 창립 멤버이자 Tesla의 AI 총괄을 지낸, AI 분야에서 가장 영향력 있는 인물 중 한 명입니다.

카파시는 일찍부터 코드를 직접 타이핑하는 대신 AI에게 코딩을 시키는 방식으로 일해왔는데, 그 과정에서 **AI가 코딩할 때 반복적으로 저지르는 실수 패턴**을 발견하고 공개적으로 정리했습니다. 예를 들면 이런 것들입니다.

- 시키지도 않은 기능을 알아서 추가한다
- 50줄이면 될 코드를 200줄로 복잡하게 만든다
- 버그 하나 고쳐달라고 했는데 옆에 있는 멀쩡한 코드까지 손댄다
- 요청이 애매하면 물어보는 대신 멋대로 추측해서 진행한다

혹시 AI에게 뭔가 시켜보신 분이라면 "아, 그거!" 하실 수도 있겠네요. 전 세계 개발자들이 똑같이 겪는 문제입니다.

이 관찰이 큰 화제가 되자, Forrest Chang이라는 개발자가 카파시의 관찰을 **CLAUDE.md 파일 하나로 압축**해서 공개했습니다. "AI야, 이런 실수를 하지 마"를 파일 하나에 담은 것이죠. 저는 이것의 **한국어 번역본**을 표준으로 사용합니다.

## 안에는 어떤 내용이 들어있나요?

크게 **4가지 원칙**이 담겨 있습니다. 먼저 한눈에 보면 이렇습니다.

| # | 원칙 | 막아주는 실수 |
|:-:|------|--------------|
| 1 | **코딩하기 전에 생각하기** | 멋대로 추측해서 진행 |
| 2 | **단순함을 최우선으로** | 과하게 복잡한 코드 |
| 3 | **필요한 부분만 수정하기** | 안 시킨 코드까지 변경 |
| 4 | **목표 중심으로 실행하기** | "고친 것 같아요"로 끝나는 작업 |

하나씩 볼게요.

### 원칙 1. 코딩하기 전에 생각하기

AI는 요청이 애매해도 일단 뭔가를 만들어냅니다. 문제는 그 과정에서 **멋대로 추측**한다는 것이죠. 이 원칙은 Claude에게 이렇게 지시합니다.

> "확실하지 않으면 추측하지 말고 **질문해라**. 여러 가지로 해석될 수 있으면 임의로 하나를 고르지 말고 **선택지를 보여줘라**."

적용하고 나면 Claude가 작업 전에 "이 부분은 A로 이해했는데 맞나요?"라고 물어보는 모습을 보실 수 있습니다.

### 원칙 2. 단순함을 최우선으로

AI는 "성실한 과잉"을 저지릅니다. 요청한 것보다 더 많이, 더 복잡하게 만드는 경향이 있어요. 이 원칙은 이렇게 지시합니다.

> "문제를 해결하는 데 필요한 **최소한의 코드**만 작성해라. 요청받지 않은 기능, 나중에 쓸 것 같은 기능은 추가하지 마라."

코드가 단순할수록 나중에 이해하기 쉽고, 고치기 쉽고, 버그도 적습니다.

### 원칙 3. 필요한 부분만 정확하게 수정하기

버그 하나 고쳐달라고 했는데 파일 전체가 바뀌어 있으면 곤란하겠죠. 뭐가 바뀐 건지 확인하기도 어렵고요. 이 원칙은 이렇게 지시합니다.

> "반드시 **필요한 부분만** 건드려라. 주변 코드를 마음대로 '개선'하지 마라. 기존 코드 스타일을 따라라."

수술하듯 정확하게, 요청과 관련된 부분만 수정하게 만드는 원칙입니다.

### 원칙 4. 목표 중심으로 실행하기

"버그 고쳐줘"라고 하면 AI는 고쳤다고 말하지만, 정말 고쳐졌는지는 알 수 없습니다. 이 원칙은 Claude에게 **검증 방법을 먼저 만들게** 합니다.

> "'버그 수정'이 아니라 '버그를 재현하는 **테스트를 만들고**, 그 테스트가 **통과할 때까지** 수정'으로 일해라."

"고친 것 같아요"가 아니라 "고쳐진 것을 확인했어요"로 바뀌는 것이죠.

> **알아두실 점 하나.** 이 지침을 적용하면 Claude가 **작업 전에 질문을 더 많이** 하게 됩니다. "빨리 안 하고 왜 자꾸 물어보지?" 싶으실 수 있는데, 이건 의도된 동작입니다. 잘못 만들어진 다음에 발견해서 다시 만드는 것보다, 만들기 전에 질문 몇 개에 답하는 쪽이 훨씬 빠르고 저렴하기 때문입니다.

## 어디에 설치되나요?

이 파일이 어디에 놓이는지 이해하면 뒤의 장들을 볼 때도 도움이 되니, 잠깐만 설명드릴게요.

Windows에는 사용자마다 **홈 디렉토리**라는 개인 공간이 있습니다. 파일 탐색기에서 보이는 `C:\Users\사용자명` 폴더가 바로 그곳입니다. 그 안에 `.claude`라는 폴더가 있는데(Claude Code를 설치하면 자동으로 생깁니다), Claude Code가 개인 설정을 보관하는 곳입니다.

우리의 CLAUDE.md는 바로 여기에 설치됩니다.

```text
C:\Users\사용자명\
  └── .claude\
      └── CLAUDE.md      ← 여기!
```

> **참고:** 터미널(PowerShell)에서는 홈 디렉토리를 물결 기호 `~` 하나로 줄여 씁니다. 앞으로 이 핸드북에서 `~\.claude\CLAUDE.md`라고 쓰면 `C:\Users\사용자명\.claude\CLAUDE.md`를 뜻하는 것입니다.

이 위치가 중요한 이유가 있습니다. CLAUDE.md는 **놓이는 위치에 따라 적용 범위가 달라지거든요.**

| 위치 | 적용 범위 | 비유하자면 |
|------|----------|-----------|
| `~\.claude\CLAUDE.md` | **모든 프로젝트** (전역) | 공통 규정 |
| 프로젝트 폴더의 `CLAUDE.md` | 그 프로젝트만 | 해당 프로젝트 업무 규칙 |

우리가 설치하는 Karpathy 지침은 어떤 프로젝트에서든 지켜져야 할 기본기라서 **전역 위치**에 둡니다. 각 프로젝트에는 그 프로젝트만의 CLAUDE.md를 따로 만들 수 있는데(3장에서 다룹니다), 그건 전역 지침을 대체하는 게 아니라 **함께** 적용됩니다. 공통 규정 위에 각 프로젝트의 규칙이 더해지는 구조입니다.

## 어떻게 설치하나요?

**직접 하실 일은 없습니다.** 셋업 스크립트(setup.ps1)를 실행하면 이 파일이 자동으로 제자리에 설치됩니다. 셋업 방법은 [저장소 README](https://github.com/jubijubiguri/claude-code-starter)에 있습니다.

혹시 수동으로 설치해야 하는 상황이 생기면, 아래를 펼쳐서 따라 해주세요.

# 2장. Hook — Claude가 선을 넘지 않게 지켜주는 자동 안전장치

> **바쁘신 분을 위한 3줄 요약**
>
> 1. Hook은 Claude가 위험하거나 규칙에 어긋나는 행동을 하려는 **순간에 자동으로 차단하는 장치**입니다.
> 2. 안전 가드(위험 명령 차단 등)는 **모두에게 자동 적용**되고, 개발 실천 가드(TDD 등)는 **원하는 팀/개인만** 켭니다.
> 3. 설치는 셋업 스크립트가 자동으로 하며, 직접 하실 일은 없습니다. 작업 중 **차단 메시지를 만나는 것은 고장이 아니라 정상 동작**입니다.

이번 장에서 소개할 것은 **Hook(훅)**이라는 자동 안전장치입니다. 1장의 CLAUDE.md가 Claude에게 주는 "지침"이었다면, Hook은 지침만으로 부족할 때를 위한 "강제 장치"입니다.

## Hook이 뭔가요?

CLAUDE.md에 "위험한 명령을 실행하지 마"라고 적어두면 Claude는 대체로 잘 따릅니다. 하지만 "대체로"입니다. 지침은 어디까지나 부탁이라서, 복잡한 작업 중에는 놓칠 수도 있습니다.

**Hook은 부탁이 아니라 시스템입니다.** Claude가 어떤 행동(명령 실행, 파일 수정 등)을 하려는 바로 그 순간, Claude와 무관하게 별도의 검사 프로그램이 자동으로 실행됩니다. 검사에 걸리면 그 행동은 실행되지 않습니다. Claude가 "깜빡"할 수는 있어도 Hook을 지나치지 않고는 행동할 수 없습니다.

건물 출입에 비유하면, CLAUDE.md는 "외부인 출입 금지" 안내문이고 Hook은 사원증을 대야 열리는 게이트입니다. 안내문은 못 볼 수도 있지만 게이트는 통과하지 않을 방법이 없죠.

## 무엇이 설치되나요?

팀 Hook은 성격에 따라 두 묶음으로 나뉩니다.

| 묶음 | 적용 | 무엇을 하나 |
|------|------|------------|
| **안전 가드** (team-guards) | 전 구성원 자동 | 되돌리기 어려운 사고를 사전 차단 |
| **개발 실천 가드** (team-dev-practice) | 팀/개인 선택 | TDD, 커밋 검증 등 개발 규율 강제 |

### 안전 가드 — 모두에게 자동 적용

**1. 위험 명령 차단 (Dangerous Command Guard)**

컴퓨터 명령 중에는 "실행 취소"가 없는 것들이 있습니다. 폴더를 통째로 지워버리는 명령(`rm -rf /` 계열), 팀이 함께 쓰는 코드 보관소의 기록을 덮어써버리는 명령(`git push --force`), 작업하던 내용을 통째로 날려버리는 명령(`git reset --hard`) 같은 것들이죠. 한 번 실행되면 되돌릴 방법이 없거나 매우 어렵습니다. 이 가드는 Claude가 그런 명령을 실행하려는 순간 멈춰 세웁니다. 작업 중 생긴 임시 파일을 지우는 것 같은 일상적인 정리(`rm -rf node_modules` 등)는 평소처럼 허용되므로, 정상적인 작업이 답답해지는 일은 없습니다.

**2. 보호 파일 차단 (Protected Files Guard)**

프로젝트 폴더 안에는 비밀번호나 서비스 접속 키처럼 유출되거나 잘못 바뀌면 안 되는 정보가 담긴 파일이 몇 개 있습니다(`.env` 계열, `credentials`, `secrets` 파일과 Git 내부 폴더인 `.git/`). 이 가드는 Claude가 그런 파일을 고치는 것 자체를 막습니다. 전역 CLAUDE.md(공통 표준)도 여기서 보호됩니다. 실수로 내용이 바뀌어 서비스가 멈추거나 보안 사고로 이어지는 일을 예방합니다.

### 개발 실천 가드 — 원하는 팀/개인만

"코드를 고치면 검사도 함께 통과해야 한다" 같은 좋은 개발 습관을, 어기고 싶어도 어길 수 없게 만들어주는 5종 세트입니다. 코드를 작성하는 팀에 유용하지만, 문서 작업이 많은 분에게는 과할 수 있어 선택제로 운영합니다.

아래 설명에서 "테스트"는 내가 만든 코드가 제대로 동작하는지 자동으로 확인해주는 검사 코드를 말합니다.

| Hook | 하는 일 |
|------|---------|
| TDD Guard | 테스트를 먼저 만들고 나서 코드를 작성하도록 순서를 지키게 합니다. 테스트 없이 코드부터 쓰려 하면 "테스트부터 만들어 달라"며 멈춰 세웁니다. |
| Bash File Change Guard | Claude가 다른 경로(터미널 명령)로 코드를 고쳐서 위의 TDD Guard를 건너뛰는 것을 막습니다. |
| Pre-commit Check | 작업 결과를 팀 코드 보관소에 저장(`git commit`)하기 직전에 자동 검사(lint / build / test)를 돌리고, 하나라도 실패하면 저장을 막습니다. 고장난 코드가 팀 전체에 공유되는 것을 막는 문지기입니다. |
| Quality Gate | Claude가 "다 했습니다"라고 말하기 전에 정말 다 됐는지 검사합니다. 통과하지 못하면 Claude는 끝내지 못하고 계속 고쳐야 합니다. |
| Circuit Breaker | 같은 시도가 3번 연속 실패하면 똑같은 시도를 또 하지 못하게 막습니다. 안 되는 방법을 붙잡고 시간과 비용을 낭비하는 것을 방지합니다. |

이 중 TDD Guard는 일하는 순서 자체를 바꾸는 가드라서, 옵트인 전에 읽어볼 별도의 장(6장)에서 자세히 다룹니다.

## 차단 메시지를 만나면 어떻게 하나요?

작업 중에 이런 메시지를 보실 수 있습니다.

```text
Dangerous Command Guard
강제 push는 원격 Git 이력을 덮어쓸 수 있습니다.
차단된 명령: git push --force origin main
이 작업이 정말 필요하면 사용자가 명령을 직접 검토한 뒤 수동으로 실행하세요.
```

**이것은 고장이 아니라 안전장치가 일한 것입니다.** 대응은 상황에 따라 다음 중 하나입니다.

1. **대부분의 경우** — Claude가 차단 사유를 읽고 스스로 더 안전한 방법을 찾아 계속 진행합니다. 지켜보시면 됩니다.
2. **그 작업이 정말 필요한 경우** — 차단된 명령을 본인이 직접 검토한 뒤 터미널에서 수동으로 실행하세요. Hook은 Claude의 행동만 검사하며, 사람이 직접 실행하는 것은 막지 않습니다.
3. **커밋 검증(Pre-commit Check)에 걸린 경우** — 먼저 실패한 lint/test를 고치는 게 정석입니다. 의식적으로 건너뛰어야 할 때만 `git commit --no-verify`를 사용하세요.

## 어떻게 설치하나요?

**안전 가드는 직접 하실 일이 없습니다.** 셋업 스크립트를 실행하면 자동으로 켜집니다. 개발 실천 가드는 설치까지만 되어 있고 꺼진 상태로 배포되며, 아래 방법으로 켭니다.

<details>
<summary><b>개발 실천 가드 켜기</b></summary>
해당 항목은 배보다 배꼽이 커질수 있습니다. 큰 규모의 프로젝트를 진행하시는 분들에게 추천하는 hook입니다. 방법은 프로젝트 저장소의 `.claude/settings.json` 파일에서 아래 값을 `true`로 바꿔 커밋하면, **그 프로젝트에 적용**됩니다.

```json
{

    "team-dev-practice@company-tools": true
  }
}
```

</details>

# 3장. 프로젝트 CLAUDE.md — 프로젝트의 기억을 만들고 키우기

> **바쁘신 분을 위한 3줄 요약**
>
> 1. 프로젝트에 CLAUDE.md가 없다면 `/init` 한 번으로 만들 수 있습니다.
> 2. 세션을 마칠 때 `/revise-claude-md`를 입력하는 습관을 들이면, **오늘 배운 것이 쌓여 다음의 Claude가 더 똑똑해집니다.**
> 3. 필요한 도구(Anthropic 공식 플러그인)는 자동 설치됩니다. 단, **전역 CLAUDE.md는 공통 표준이므로 수정 대상이 아닙니다** — 모든 관리는 프로젝트 CLAUDE.md에만.

1장에서 우리는 모든 프로젝트에 공통 적용되는 전역 CLAUDE.md를 설치했습니다. 이번 장에서는 **각 프로젝트가 자기만의 CLAUDE.md를 갖고, 그 문서가 시간이 갈수록 똑똑해지게 만드는 방법**을 다룹니다.

## 전역과 프로젝트, 두 개의 CLAUDE.md

1장에서 봤던 표를 다시 떠올려보세요.

| 위치 | 적용 범위 | 이번 장에서 |
|------|----------|----------------|
| `~\.claude\CLAUDE.md` (전역) | 모든 프로젝트 | **손대지 않습니다** (공통 표준) |
| 프로젝트 폴더의 `CLAUDE.md` | 그 프로젝트만 | **여기가 주인공입니다** |

전역 파일은 모두가 똑같이 쓰는 "공통 규정"입니다. 반면 프로젝트 CLAUDE.md는 그 프로젝트만의 지식 — 테스트 돌리는 법, 건드리면 안 되는 설정, 그 프로젝트에서만 통하는 규칙 — 을 담는 곳이고, 프로젝트와 함께 성장해야 하는 살아있는 문서입니다. 이번 장의 모든 도구는 **프로젝트 CLAUDE.md만** 대상으로 사용합니다.

## 프로젝트에 CLAUDE.md가 아직 없다면 — 만들기

새 프로젝트를 만들었거나 기존 레포를 처음 여는 경우, CLAUDE.md는 자동으로 생기지 않습니다. 직접 만들 필요도 없습니다. 프로젝트 폴더에서 Claude Code를 열고 아래를 입력하세요.

```text
/init
```

Claude가 프로젝트 구조를 훑어보고 CLAUDE.md 초안을 만들어줍니다. 초안이니 완벽하지 않아도 괜찮습니다 — 아래 도구들로 계속 다듬어갈 것이기 때문입니다. 만들어진 파일은 프로젝트에 포함되도록 커밋해주세요.

## 매일의 습관 — /revise-claude-md

이 장에서 딱 하나만 기억하신다면 이것입니다. **작업 세션을 마칠 때, 아래 한 줄을 입력하는 습관.**

```text
/revise-claude-md
```

그러면 Claude가 방금 세션을 돌아보며 "다음에 알았으면 좋았을 것들"을 찾아 CLAUDE.md에 한 줄씩 정리해줍니다. 예를 들면 이런 것들입니다.

- 오늘 헤매다 알아낸 빌드/테스트 명령
- "이 파일은 건드리면 안 된다" 같은 함정
- 이 프로젝트가 따르는 코드 스타일

이게 왜 중요할까요? 오늘 Claude가 30분 헤매서 알아낸 사실을 기록해두지 않으면, 다음 세션의 Claude는 **또 30분을 헤맵니다.** 기록해두면 다음부터는 0분입니다. 이 한 줄들이 쌓이면 Claude가 프로젝트를 점점 더 잘 아는 동료가 되어갑니다 — 저축처럼 복리로 불어나는 효과입니다.

실행하면 Claude가 저장 위치를 물어볼 수 있습니다. 기준은 간단합니다.

- **그 프로젝트에서 계속 유효한 내용** → `CLAUDE.md` (커밋해서 프로젝트에 남김. 함께 일하는 사람이 있다면 공유됨)
- **내 컴퓨터에만 해당하는 내용** (개인 환경 설정 등) → `.claude.local.md` (커밋되지 않는 개인 메모. 보통 Claude가 만들면서 `.gitignore`에 함께 등록해주는데, 커밋 목록에 이 파일이 보이면 `.gitignore`에 추가해주세요)

## 가끔의 점검 — CLAUDE.md 정밀 검진

CLAUDE.md가 오래되어 실제 코드와 어긋났거나, 너무 길어졌거나, 처음부터 대충 만들어진 것 같을 때는 정밀 검진을 시키세요. 자연어로 말하면 됩니다.

```text
CLAUDE.md 품질 점검해줘
```

"CLAUDE.md 검사해줘", "감사해줘", "개선해줘", "고쳐줘", "업데이트해줘" 같은 표현도 다 알아듣습니다. Claude가 프로젝트의 CLAUDE.md 파일들을 찾아 품질 리포트를 보여주고, **여러분의 승인을 받은 뒤** 개선을 적용합니다.

> **참고:** 이 점검은 전역 파일(`~\.claude\CLAUDE.md`)까지 찾아내서 개선을 제안할 수 있습니다. 걱정하실 것은 없습니다 — 전역 파일은 공통 표준이라 **2장의 안전 가드가 수정을 자동으로 차단**하며, 실수로 승인해도 적용되지 않습니다. 프로젝트 CLAUDE.md에 대한 제안만 승인하며 진행하시면 됩니다.

다음 장의 AI-Ready 진단과 함께 쓰면 좋습니다. 진단에서 "Context Quality(문서 품질)"가 약점으로 나왔다면, 그 치료가 바로 이 점검입니다.

# 4장. AI-Ready 진단 — 내 프로젝트는 Claude와 일할 준비가 됐을까

> **바쁘신 분을 위한 3줄 요약**
>
> 1. Claude가 유독 헤매는 프로젝트가 있다면, 문제는 Claude가 아니라 **프로젝트 구조일 가능성**이 높습니다.
> 2. Claude에게 "이 레포 AI-readiness 점수 매겨줘" 한 마디만 하면 **100점 만점 진단표와 개선 처방전**이 나옵니다.
> 3. 별도 설치는 없습니다. 셋업이 끝났다면 이미 쓸 수 있는 상태입니다.

이번 장은 앞의 장들과 성격이 다릅니다. CLAUDE.md(1장)와 Hook(2장)이 설치해두면 알아서 작동하는 장치였다면, **AI-Ready 진단**은 여러분이 필요할 때 직접 꺼내 쓰는 도구입니다.

## 왜 이런 도구가 필요한가요?

같은 Claude인데 어떤 프로젝트에서는 척척 일하고, 어떤 프로젝트에서는 엉뚱한 파일을 뒤지며 헤맵니다. 왜 그럴까요?

Claude가 실패하는 원인의 대부분은 코드가 나빠서가 아니라 **길을 못 찾아서**입니다. 어디가 시작점인지, 뭐가 뭐에 연결되는지, 팀만 아는 암묵적인 규칙이 뭔지 — 사람이라면 옆자리 동료에게 물어볼 것들이 문서로 남아있지 않으면, Claude는 매번 처음 온 신입처럼 헤맵니다.

**AI-Ready 진단은 내 프로젝트가 Claude에게 얼마나 "길 안내"를 잘하고 있는지 채점하는 건강검진입니다.** 점수만 주는 게 아니라, 어디를 고치면 효과가 가장 큰지 우선순위까지 뽑아줍니다.

## 언제 돌려보면 되나요?

정기 검사가 아니라, **증상이 느껴질 때** 돌리는 도구입니다.

- Claude가 이 레포에서 유독 엉뚱한 파일을 찾거나 같은 실수를 반복할 때
- "왜 이렇게 되어 있어요?"라고 Claude가 물었는데 나도 설명할 문서가 없을 때
- 새 프로젝트에서 Claude Code를 본격적으로 쓰기 시작할 때
- 프로젝트 문서를 정비한 뒤, 나아졌는지 확인하고 싶을 때

## 어떻게 실행하나요?

프로젝트 폴더에서 Claude Code를 열고, 이렇게 말하면 끝입니다.

```text
이 레포 AI-readiness 점수 매겨줘
```

비슷한 표현도 다 알아듣습니다. "이 프로젝트 Claude가 잘 다룰 수 있는 상태인지 진단해줘"라고 해도 됩니다. Claude가 알아서 채점 스크립트를 돌리고, 결과 대시보드를 만들어 브라우저로 열어줍니다. 1~2분이면 끝납니다.

## 결과는 어떻게 읽나요?

결과물은 한 장짜리 대시보드(HTML)입니다. 세 부분만 보시면 됩니다.

**1. 총점과 등급**

| 점수 | 등급 | 의미 |
|------|------|------|
| 90~100 | AI-Native | Claude가 팀원처럼 일할 수 있는 상태 |
| 75~89 | AI-Ready | 준비됨. 대부분의 작업을 믿고 맡길 수 있음 |
| 60~74 | AI-Assisted | 쓸 수는 있지만 자주 헤맴. 개선 여지 큼 |
| 40~59 | AI-Fragile | Claude가 실수하기 쉬운 구조. 정비 권장 |
| 40 미만 | AI-Hostile | 길 안내가 거의 없음. 정비부터 시작 |

처음 돌렸는데 점수가 낮아도 놀라지 마세요. 대부분의 프로젝트가 낮게 시작합니다. 이 점수는 "Claude를 쓸 자격"이 아니라 **어디부터 고칠지 알려주는 출발점**입니다.

**2. 7개 영역별 점수**

무엇이 부족한지 영역별로 보여줍니다.

| 영역 | 무엇을 보나 |
|------|------------|
| Navigation | 시작점과 구조를 찾을 수 있게 안내되어 있나 |
| Context Quality | 안내 문서(CLAUDE.md 등)가 정확하고 쓸모 있나 |
| Tribal Knowledge | 팀만 아는 암묵적 규칙이 문서로 남아있나 |
| Dependency Mapping | 뭐가 뭐에 연결되는지 드러나 있나 |
| Verification Gates | 결과를 검증할 장치(테스트 등)가 있나 |
| Freshness | 문서가 실제 코드와 어긋나지 않았나 |
| Agent Outcomes | 실제로 Claude가 이 레포에서 잘 일하고 있나 |

**3. 개선 액션 리스트 (가장 중요)**

"이걸 고치면 효과가 이만큼"이 **가성비 순으로 정렬**되어 나옵니다. 전부 할 필요 없습니다. **상위 1~2개만 적용해도 체감이 달라집니다.** 그리고 그 적용도 Claude에게 시키면 됩니다.

```text
액션 리스트 1번 적용해줘
```

적용 후 다시 진단을 돌려서 점수가 올랐는지 확인하는 것까지가 한 사이클입니다.

## 결과는 팀과 공유하세요

진단 결과 파일(`docs/ai-readiness-map.html`)은 프로젝트에 커밋해두는 것을 권장합니다. 두 가지 이유입니다.

- 팀원 누구나 열어볼 수 있고, 다음 진단 때 점수 추이를 비교할 수 있습니다.
- 같은 레포에서 여러 명이 각자 개선 작업을 하면 중복될 수 있으니, 어떤 액션을 적용할지는 팀 채널에 한 줄 공유하고 진행하세요.

# 5장. 토큰 효율 — 내가 쓰는 비용, 얼마나 되고 어떻게 줄일까

> **바쁘신 분을 위한 3줄 요약**
>
> 1. Claude Code는 주고받는 글자량(토큰)에 비례해 비용이 발생합니다. 같은 일도 **습관에 따라 비용이 몇 배씩 차이** 납니다.
> 2. "토큰 효율 분석해줘" 한 마디면 내 세션 기록을 분석해 **비용 대시보드와 "이렇게 하면 $얼마 절감" 제안**을 만들어줍니다.
> 3. 분석은 **전부 내 컴퓨터 안에서** 이루어집니다. 대화 내용이 어디로 전송되지 않습니다.

Claude Code는 쓰는 만큼 비용이 나가는 도구입니다. 이번 장은 **내가 실제로 얼마를 어떻게 쓰고 있는지 확인하고, 아낄 수 있는 부분을 찾아주는 진단 도구**를 소개합니다. 4장의 AI-Ready 진단이 "프로젝트 건강검진"이었다면, 이건 "내 사용 습관 건강검진"입니다.

## 토큰이 뭐고, 왜 비용인가요?

Claude는 주고받는 모든 글을 **토큰**이라는 단위로 처리하고, 비용은 토큰 수에 비례합니다. 대략 한국어 1글자가 1.5토큰쯤입니다. 중요한 것은 내가 입력한 글자만 세는 게 아니라는 점입니다 — Claude가 읽은 파일, 실행 결과, 대화 이력 전체가 매번 토큰으로 계산됩니다.

그래서 같은 작업이라도 습관에 따라 비용이 크게 달라집니다. 큰 파일을 여러 번 반복해서 읽게 하거나, 한 세션을 끝없이 길게 끌면 비용이 몇 배로 뜁니다. 문제는 이게 **눈에 안 보인다**는 것이죠. 이 도구는 그걸 보이게 만듭니다.

## 비용의 핵심 원리: 캐시 — 같은 내용은 싸고, 바뀐 내용은 비싸다

습관 이야기 전에 원리 하나만 이해하고 가면 모든 습관이 납득됩니다.

Claude는 매번 대화 전체(지침, 읽은 파일, 지금까지의 이력)를 다시 처리해야 합니다. 다만 **앞부분이 지난번과 완전히 똑같으면**, 다시 보내는 대신 "캐시"라는 임시 저장소에서 재사용합니다. 캐시에서 읽는 비용은 새로 처리하는 비용의 **약 10분의 1**입니다. 대화가 길어져도 비용이 감당되는 이유가 이것입니다.

그런데 캐시에는 규칙이 두 개 있습니다.

- **앞부분이 조금이라도 바뀌면, 바뀐 지점부터 전부 다시 등록**해야 합니다. 등록(쓰기)은 평소 처리보다 오히려 비쌉니다. "고정된 내용은 앞에, 자주 바뀌는 내용은 뒤에"가 유리한 이유입니다.
- **몇 분 동안 사용하지 않으면 만료**됩니다. 다시 쓰려면 재등록 비용이 듭니다.

이 원리에서 아래 습관들이 전부 따라 나옵니다.

## 실제로 토큰을 줄이는 습관

| 하지 마세요 | 대신 이렇게 | 왜 |
|---|---|---|
| 같은 파일을 반복해서 읽게 하기 | 자주 쓰는 정보는 프로젝트 CLAUDE.md에 기록 | 기록은 캐시에 실려 거의 공짜, 반복 읽기는 매번 과금 |
| 한 세션을 끝없이 길게 끌기 | 작업 단위가 끝나면 `/compact` | 이력 전체가 매번 처리량에 포함됨 — 요약본으로 압축 |
| 주제가 바뀌어도 이어서 하기 | 새로운 일은 새 세션에서 | 무관한 이력까지 계속 비용에 포함됨 |
| 수시로 `/clear` 하기 | 세션은 유지하고 `/compact` 활용 | `/clear`는 쌓아둔 캐시를 버리고 재등록하는 것 |
| 모든 작업을 최고 성능 모델로 | 간단한 작업은 `/model`에서 가벼운 모델 선택 | 모델 간 가격 차이가 약 5배 — 단순 조회·정리엔 과함 |
| 스크린샷을 통째로 붙여넣기 | 필요한 부분만 잘라서 붙이기 | 이미지 한 장이 수만 토큰이고, 세션이 끝날 때까지 계속 실려 다님 |
| 5분 간격으로 찔끔찔끔 물어보기 | 물어볼 것을 모아서 몰아 작업하기 | 캐시가 만료되면 물음마다 재등록 비용 발생 |

몇 가지만 부연하면:

- **`/compact`는 이 목록에서 가장 효과가 큽니다.** 긴 세션의 이력을 요약본으로 바꿔 이후 모든 턴의 비용을 낮춥니다. 큰 작업 하나가 끝났을 때가 적기입니다.
- **모델 변경은 `/model` 한 번이면 됩니다.** 생산 실적 데이터를 정리해서 표로 만드는 정도의 작업은 가벼운 모델도 충분히 잘합니다. 복잡한 설계·구현에만 상위 모델을 쓰세요.
- **이미지는 특히 조심하세요.** 화면 전체 스크린샷을 붙이고 대화를 계속하면, 그 이미지가 매 턴 실려 다닙니다. 문제가 해결됐으면 `/compact`로 정리하는 게 좋습니다.

그런데 이 중에 **나는 어떤 습관부터 고치는 게 효과가 클까요?** 사람마다 다릅니다. 그걸 내 실제 기록으로 알려주는 것이 지금부터 소개할 진단 도구입니다.

## 이 도구가 뭘 해주나요?

Claude Code는 모든 세션의 사용 기록을 내 컴퓨터에 자동으로 남깁니다. 이 도구는 그 기록을 분석해서 한 장짜리 대시보드를 만들어줍니다.

- **총비용과 토큰 사용량** — 이 프로젝트에서 지금까지 얼마를 썼는지
- **세션별 순위** — 어떤 세션이 비쌌는지 (보통 상위 몇 개가 비용 대부분을 차지합니다)
- **효율 점수와 등급** (A+~F) — 내 사용 습관이 얼마나 알뜰한지
- **개선 카드** — "이 습관을 바꾸면 약 $얼마 절감" 형태의 구체적 제안

## 언제 돌려보면 되나요?

4장의 진단처럼 정기 검사가 아니라 궁금할 때 돌리는 도구입니다.

- 이번 달 사용량이 왜 이렇게 나왔는지 궁금할 때
- 사용 한도에 자주 걸려서 뭐가 문제인지 알고 싶을 때
- Claude Code를 한 달쯤 써봤고, 내 습관을 한번 점검하고 싶을 때

## 어떻게 실행하나요?

프로젝트 폴더에서 Claude Code를 열고 이렇게 말하면 됩니다.

```text
토큰 효율 분석해줘
```

"이 프로젝트 Claude 비용 분석해줘", "세션 효율 리포트 만들어줘" 같은 표현도 알아듣습니다. Claude가 기록을 분석하고 대시보드를 브라우저로 열어준 뒤, 핵심 수치와 가장 효과 큰 개선 2~3가지를 요약해줍니다.

## 결과에서 뭘 보면 되나요?

대시보드에 차트가 많지만, 두 가지만 보시면 충분합니다.

**1. 개선 카드 (가장 중요)** — "이렇게 하면 약 $얼마"가 붙은 제안 목록입니다. 전부 할 필요 없이 **금액이 큰 위쪽 1~2개**만 실천해도 체감됩니다. 단, 이 금액은 휴리스틱 추정치라 참고용입니다 — 실천 후 다시 분석해서 실제 변화를 확인하는 것까지가 한 사이클입니다.

**2. 효율 점수의 근거** — 점수는 네 가지 습관을 봅니다.

| 지표 | 쉽게 말하면 |
|------|------------|
| 캐시 활용 | 같은 내용을 매번 다시 보내지 않고 재사용하고 있는가 |
| 산출 밀도 | 읽기만 잔뜩 하고 결과물은 적은 "헛바퀴"가 없는가 |
| 중복 읽기 | 같은 파일을 여러 번 반복해서 읽고 있지 않은가 |
| 도구 경제성 | 결과물 대비 도구 호출이 과하지 않은가 |

# 6장. TDD Guard — 테스트가 먼저인 개발

> **바쁘신 분을 위한 3줄 요약**
>
> 1. TDD는 "검사(테스트)를 먼저 만들고, 그 검사를 통과하는 코드를 만드는" 개발 방식입니다.
> 2. Claude가 만든 코드가 **정말 맞는지 확인할 신호**가 테스트입니다 — 그래서 AI와 일할수록 더 중요해집니다.
> 3. 가드를 켜도 여러분이 할 일은 평소와 같습니다. "기능 만들어줘"라고 하면 **Claude가 알아서 테스트부터** 만듭니다.

2장에서 개발 실천 가드(옵트인 묶음)를 소개하면서 TDD Guard를 표 한 줄로만 언급했는데, 이 가드는 다른 것들과 성격이 다릅니다. 위험 명령 차단 같은 가드는 사고만 막을 뿐 일하는 방식을 바꾸지 않지만, **TDD Guard는 켜는 순간 일하는 순서 자체가 바뀝니다.** 그래서 옵트인하기 전에 읽어볼 장을 따로 준비했습니다.

## TDD가 뭔가요?

TDD(Test-Driven Development)는 순서를 뒤집는 개발 방식입니다. 보통은 코드를 만들고 나서 잘 되는지 확인하죠. TDD는 반대로 **"잘 되는지 확인하는 방법"을 먼저 만듭니다.**

1. 이 기능이 제대로 동작하면 통과하는 **검사(테스트)를 먼저 작성**합니다. 당연히 지금은 실패합니다 — 기능이 아직 없으니까요.
2. 그 검사를 **통과하는 코드를 작성**합니다.
3. 검사가 통과하면, 기능이 동작한다는 **증거**가 생긴 것입니다.

핵심은 "다 만든 것 같아요"와 "검사를 통과했어요"의 차이입니다. 전자는 느낌이고, 후자는 사실입니다.

## 왜 Claude와 일할 때 더 중요한가요?

Claude는 코드를 빠르게 많이 만들어냅니다. 그런데 그 코드가 맞는지 누가 확인하나요? 사람이 전부 읽어보는 건 현실적으로 어렵고, "Claude가 맞다고 했으니까"는 확인이 아닙니다.

**테스트가 있으면 확인이 자동화됩니다.** 그리고 더 큰 장점이 있습니다 — 1장의 원칙 4("목표 중심으로 실행하기")를 기억하시나요? 테스트는 Claude에게 줄 수 있는 가장 명확한 목표입니다.

```text
"이 테스트가 통과할 때까지 구현해줘"
```

이렇게 맡기면 Claude는 스스로 실행하고, 실패를 보고, 고치고, 다시 실행하는 **자기 검증 반복**을 돌립니다. 사람은 중간 과정을 감시하는 대신 통과라는 결과만 확인하면 됩니다. 믿고 맡기는 범위가 넓어지는 것이죠.

## Guard가 정확히 뭘 막고, 뭘 허용하나요?

TDD Guard는 Claude가 **테스트 없는 소스 코드를 작성하려는 순간**에만 개입합니다. 모든 파일에 테스트를 요구하는 게 아닙니다.

| 구분 | 대상 |
|------|------|
| **검사함** | 소스 코드 파일 (`.ts` `.tsx` `.js` `.jsx`) — 대응하는 테스트 파일이 있는지 확인 |
| **그냥 허용** | 테스트 파일 자체, 설정 파일(json/yml 등), 스타일(css/scss), 문서(md), 타입 정의, Next.js 프레임워크 파일(layout, page 등) |

테스트 없는 소스 파일을 작성하려 하면 Claude에게 이런 메시지가 전달됩니다.

```text
TDD GUARD: 'foo'에 대한 테스트 파일이 존재하지 않습니다.
구현 코드를 작성하기 전에 테스트를 먼저 작성하세요. (테스트 파일 예: foo.test.ts)
```

그리고 짝꿍 가드가 하나 함께 켜집니다. **Bash File Change Guard**는 Claude가 터미널 명령으로 소스 파일을 고쳐서 이 검사를 건너뛰는 우회로를 막습니다. 문과 창문을 같이 잠그는 셈입니다.

## 실제 작업 흐름은 어떻게 되나요?

여러분이 특별히 바꿀 것은 없습니다. 평소처럼 요청하세요.

```text
설비별 생산 실적을 조회하는 기능 만들어줘
```

가드가 켜져 있으면 이렇게 흘러갑니다: Claude가 구현 파일을 만들려다 가드에 멈춤 → 차단 사유를 읽고 **테스트부터 작성**(예: "설비 코드를 넣으면 해당 설비의 실적만 나오는가", "없는 설비 코드를 넣으면 빈 결과를 주는가") → 구현 작성 → 테스트 실행해서 통과 확인 → 완료 보고. 여러분에게 달라지는 것은 결과물에 항상 "통과한 테스트"라는 증거가 함께 온다는 점입니다. 조회 화면이 그럴듯하게 떠서가 아니라, 검증을 통과했기 때문에 믿을 수 있게 되는 것이죠.

## 켜는 법

TDD Guard는 개발 실천 가드(team-dev-practice) 묶음에 들어 있고, 켜는 방법은 2장의 "개발 실천 가드 켜기"와 같습니다 — 프로젝트의 `.claude/settings.json`에서 `team-dev-practice@company-tools`를 `true`로 바꾸면 됩니다.

전체 코드에 테스트를 한꺼번에 만들 필요는 없습니다. 가드는 **지금 만들거나 고치려는 파일**만 검사하므로, 켠 시점부터 손대는 파일마다 테스트가 하나씩 생기는 점진적 방식으로 굴러갑니다. 다만 기존 파일을 고칠 때도 그 파일의 테스트부터 만들게 되므로, 초반에는 작업마다 테스트 작성 시간이 추가된다는 점은 감안하세요.

# 7장. SDD — 크게 만들 때는 스펙부터

> **바쁘신 분을 위한 3줄 요약**
>
> 1. SDD(Spec-Driven Development)는 **만들기 전에 "무엇을 왜 만드는지"를 문서로 합의**하고, 그 합의대로 단계를 나눠 실행하는 방식입니다.
> 2. 반나절짜리 작업에는 과합니다. **여러 날 걸리는 크고 모호한 작업**에만 쓰세요 — 중간 크기는 내장 플랜 모드면 충분합니다.
> 3. 필요해지는 순간 "이 프로젝트에 SDD 세팅해줘" 한 마디면 도구 일체가 설치됩니다. 미리 준비할 것은 없습니다.

지금까지의 도구들이 "Claude가 실수하지 않게" 만드는 것이었다면, 이번 것은 **"크고 모호한 것을 만들 때 방향이 어긋나지 않게"** 만드는 일하는 방식입니다. 모든 작업에 쓰는 것이 아니니, 언제 쓰는지부터 정확히 알려드릴게요.

## SDD가 뭔가요?

작은 작업은 "만들어줘" 한 마디로 충분합니다. 그런데 크고 모호한 작업 — 예를 들어 "생산 데이터 분석 대시보드를 처음부터" — 을 그렇게 시작하면, Claude는 모호한 부분을 자기 나름대로 채우면서 만들어 나갑니다. 사흘 뒤에 결과를 보면 열심히 만들긴 했는데 **내가 원한 것과 다른 물건**이 나와 있죠. 문제는 Claude의 실력이 아니라, 합의된 기준이 없었다는 것입니다.

SDD는 순서를 바꿉니다.

1. **스펙 합의** — 무엇을(PRD), 어떤 구조로(ARCHITECTURE), 왜 그렇게(ADR) 만드는지 짧은 문서로 먼저 정합니다. 문서 작성도 Claude가 질문하며 도와줍니다.
2. **단계 분해** — 합의된 스펙을 작은 step들로 나눕니다 (`/harness` 커맨드).
3. **자동 실행** — 각 step을 Claude가 순서대로 실행합니다. 매 step마다 스펙 문서를 다시 읽고, 완료 기준을 검증하고, 실패하면 3회까지 스스로 교정합니다 (`execute.py`).
4. **검토** — 결과가 스펙을 지켰는지 확인합니다 (`/review`).

핵심은 3일 뒤가 아니라 **시작하기 전에** 방향을 맞춘다는 것입니다.

## TDD와는 뭐가 다른가요? 같이 쓰나요?

6장의 TDD와 헷갈리기 쉬운데, 둘은 경쟁 관계가 아니라 **높이가 다른 장치**입니다.

| | TDD (6장) | SDD (이번 장) |
|---|---|---|
| 지키는 것 | 코드 한 조각이 **맞는가** | 작업 전체가 **맞는 방향인가** |
| 단위 | 파일/함수 (분 단위 루프) | 프로젝트/기능 묶음 (일 단위 흐름) |
| 비유 | 벽돌 하나하나의 품질 검사 | 건물의 설계도와 공정표 |

설계도가 벽돌 검사를 대체하지 않듯, 둘은 포개서 씁니다. 실제로 SDD의 각 step은 완료 기준에 테스트 통과를 포함하고 있어서, **SDD로 일하는 프로젝트는 TDD Guard(team-dev-practice)를 함께 켜는 것을 권장**합니다.

## 언제 쓰나요? — 작업 크기별 3단계

이 표 하나만 기억하시면 됩니다.

| 작업 크기 | 예 | 방법 |
|---|---|---|
| **소형** (반나절) | 설비별 생산 실적 조회 기능 하나, 버그 수정 | 그냥 대화 — 아무것도 추가로 필요 없음 |
| **중형** (2~3일) | 조회 + 필터 + 내보내기 기능 묶음 | **플랜 모드** — 구현 전에 계획을 보고 승인 |
| **대형** (여러 날, 모호함) | 생산 데이터 분석 대시보드를 처음부터 | **SDD** — 스펙 합의 + 단계 분해 + 자동 실행 |

플랜 모드는 Claude Code에 내장된 기능입니다. Shift+Tab을 눌러 켜거나 "계획부터 세워줘"라고 말하면, Claude가 코드를 건드리기 전에 계획을 보여주고 승인을 받습니다. SDD의 "합의 먼저" 정신을 문서 없이 가볍게 쓰는 셈이라, **애매하면 플랜 모드부터 써보고, 그걸로 부족할 때 SDD로 올라가면 됩니다.**

## 시작하는 법

미리 설치할 것은 없습니다. 대형 작업을 시작하기로 한 그 시점에, 프로젝트 폴더에서 이렇게 말하세요.

```text
이 프로젝트에 SDD 세팅해줘
```

Claude가 다음을 만들어줍니다 (이미 있는 파일은 건드리지 않습니다):

- `docs/` — 스펙 문서 골격 4개 (PRD, ARCHITECTURE, ADR, UI 가이드)
- `/harness`, `/review` 커맨드
- `scripts/execute.py` — step 자동 실행기

이미 진행 중인 프로젝트에도 똑같이 됩니다. "간단하게 시작했는데 커져버렸다" 싶은 순간이 바로 세팅할 때입니다.

세팅 후 흐름은 Claude가 안내해주지만 요약하면: **스펙 채우기**(Claude가 질문하며 초안 작성) → **`/harness`로 step 분해**(초안을 보고 승인) → **실행**:

```powershell
python scripts/execute.py 작업이름
```

## 알아두실 점 — 자동 실행과 안전장치

`execute.py`는 각 step을 **권한 확인 없이 자동으로** 실행합니다. 사람이 매 단계를 승인하지 않아도 진행된다는 뜻이라 편리하지만, 그만큼 2장의 안전 가드가 안전망 역할을 합니다 — 위험 명령과 보호 파일 차단은 자동 실행 중에도 그대로 작동합니다. 안전 가드가 켜진 환경(셋업 완료 상태)에서 사용하세요.

# 8장. LLM Wiki — Claude와 함께 쓰는 지식 창고

> **바쁘신 분을 위한 3줄 요약**
>
> 1. LLM Wiki는 조사 자료, 결정 이력, 회의 내용 같은 **흩어진 지식을 한곳에 모아 Claude가 참조하게 만드는 지식 창고**입니다.
> 2. 사람은 원본을 던져 넣기만 하면 됩니다. **정리(분류·연결·색인)는 Claude가 합니다.**
> 3. 쌓일수록 가치가 커집니다 — 6개월 전의 "이 결정 왜 했더라?"를 다시 조사하지 않아도 됩니다.

마지막 장은 짧습니다 — LLM Wiki는 별도의 상세 가이드가 이미 있어서, 여기서는 **이게 어떤 용도인지**만 정리하고 상세 사용법은 링크로 안내합니다.

## 어떤 용도인가요?

일하다 보면 지식이 여기저기 흩어집니다. 조사해서 알아낸 것은 브라우저 탭에, 결정한 이유는 메신저 어딘가에, 회의 내용은 각자의 기억 속에. 시간이 지나면 "그때 왜 그렇게 하기로 했더라?"를 **처음부터 다시 조사**하게 되죠.

LLM Wiki는 이런 지식을 마크다운 파일로 한곳에 모아두는 창고입니다. 두 가지가 일반 메모장과 다릅니다.

**첫째, 정리를 Claude가 합니다.** 지식 관리가 실패하는 이유는 정리가 귀찮아서입니다. LLM Wiki에서는 사람이 원본(메모, 링크, 회의록)을 던져 넣기만 하면, 분류하고 서로 연결하고 색인을 만들고 낡은 내용을 정리하는 일은 Claude가 맡습니다.

**둘째, Claude가 참조하는 창고입니다.** 작업 중에 Claude가 "지난번에 이 주제 조사한 것 있나?"를 위키에서 찾아 활용합니다. 매번 다시 조사하는 대신 **한 번 정리된 지식이 계속 재사용**되는 것이죠. 정리된 답변이 다시 위키에 쌓이면서, 쓸수록 창고의 가치가 커집니다.

## CLAUDE.md와는 뭐가 다른가요?

간단히 구분하면 이렇습니다.

| | CLAUDE.md (1장·3장) | LLM Wiki (이번 장) |
|---|---|---|
| 담는 것 | **일하는 방식** (규칙, 명령어, 함정) | **알고 있는 것** (조사, 결정, 이력) |
| 분량 | 짧게 유지 (매 세션 읽힘) | 길어져도 됨 (필요할 때 찾아 읽음) |

## 언제 쓰면 좋나요?

- 조사·리서치를 마쳤을 때 — 결과를 위키에 남겨두면 다음에 재조사하지 않습니다
- 중요한 결정을 내렸을 때 — "왜"를 남겨두면 6개월 뒤의 나(와 Claude)가 고마워합니다
- 같은 질문을 두 번째로 조사하고 있다는 것을 깨달았을 때 — 지금이 위키를 시작할 때입니다
