# Claude Code 온보딩 코스 — 설치부터 심화까지, 치면서 배우는 따라하기

이 문서는 읽는 문서가 아니라 **치는 문서**입니다. 아무것도 설치되지 않은 컴퓨터에서 시작해, 아래 STEP의 명령과 프롬프트를 순서대로 입력(복사해서 붙여넣기)하기만 하면 [핸드북](claude-code-handbook.md)에서 설명한 도구 전부를 직접 체험하게 됩니다. 원리가 궁금해지면 그때 핸드북의 해당 장을 펴보시면 됩니다.

## 시작하기 전에 알아둘 것 세 가지

**첫째, 연습용 업무 케이스로 진행합니다.** "생산 실적 리포트 도구"라는 작은 프로그램을 Claude와 함께 만들 겁니다. 생산 기록(CSV 파일)을 읽어 월별 생산량과 라인별 불량률을 보여주는 간단한 도구인데, 이 예제 자체가 목적이 아닙니다. 만드는 과정에서 만나게 되는 **장면들** — Claude가 먼저 질문하는 모습, 안전장치가 위험한 명령을 차단하는 모습, 진단 점수가 오르는 모습 — 을 한 번씩 눈으로 봐두는 것이 목적입니다. 실전에서 그 장면을 다시 만났을 때 당황하지 않게요.

**둘째, 중간중간 "허용하시겠습니까?" 창이 뜹니다.** Claude Code는 파일을 만들거나 명령을 실행하기 전에 여러분에게 허락을 구합니다. 이 코스에서는 어떤 작업인지 한 줄 읽어보고 허용해주시면 됩니다. 연습용 빈 폴더에서 진행하므로 잘못될 것이 없습니다.

**셋째, 막히면 Claude에게 물어보세요.** 어느 STEP에서든 예상과 다른 일이 생기면 그대로 물어보면 됩니다 — "방금 왜 차단됐어?", "이 오류가 무슨 뜻이야?". 문서를 뒤지는 게 아니라 Claude에게 묻는 것, 그게 이 도구의 기본 사용법입니다.

**소요 시간** — 0부(설치) 약 15분, 1부(기본) 약 40분, 2부(심화, 선택) 약 30분. 꼭 한 번에 다 할 필요는 없습니다. 팀 셋업을 이미 마친 분은 0부를 건너뛰고 1부부터 시작하세요.

## 0부 — 설치 (약 15분)

### STEP 0. 준비물 확인

시작 버튼을 누르고 `PowerShell`을 검색해 실행한 뒤, 아래 세 명령을 한 줄씩 입력해보세요. 각각 버전 번호가 출력되면 준비된 것입니다.

```powershell
node --version
git --version
claude --version
```

**하나라도 `찾을 수 없습니다` 오류가 나면:**

- `node` 없음 → [nodejs.org](https://nodejs.org/)에서 **LTS 버전**을 내려받아 설치하세요. 설치 중 옵션은 전부 기본값으로 "다음"만 누르면 됩니다. 안전장치(Hook)가 동작하려면 반드시 필요합니다.
- `git` 없음 → [git-scm.com](https://git-scm.com/)에서 내려받아 설치하세요. 역시 기본값으로 진행하면 됩니다.
- `claude` 없음 → Claude Code가 아직 설치 전입니다. [공식 설치 안내](https://code.claude.com/docs)를 따라 설치하세요. 버전이 2.1.139보다 낮으면 뒤의 셋업 스크립트가 알려주니, 그때 `claude update`를 실행하면 됩니다.

설치했다면 **PowerShell을 닫았다가 새로 열고** 위 명령으로 다시 확인하세요.

### STEP 1. 온보딩 키트 받기 — git clone

팀의 공통 표준과 안전장치가 들어 있는 저장소를 내 컴퓨터로 복사합니다. PowerShell에서:

```powershell
cd ~\Documents
git clone https://github.com/jubijubiguri/claude-code-starter.git
```

`git clone`은 "인터넷의 저장소를 내 컴퓨터로 통째로 복사"하는 명령입니다. 실전에서 팀 프로젝트에 합류할 때도 늘 이 명령으로 시작하게 됩니다.

**이렇게 되면 성공** — `Documents` 폴더 안에 `claude-code-starter` 폴더가 생깁니다.

**만약 git이 어렵다면** — [GitHub 페이지](https://github.com/jubijubiguri/claude-code-starter)에서 `Code → Download ZIP`을 받아 압축을 풀어도 똑같습니다.

### STEP 2. 셋업 스크립트 실행

받은 폴더로 이동해 셋업 스크립트를 실행합니다.

```powershell
cd claude-code-starter
powershell -ExecutionPolicy Bypass -File .\setup.ps1
```

> `-ExecutionPolicy Bypass`는 "인터넷에서 받은 스크립트는 실행하지 않는다"는 Windows 기본 정책을 이번 한 번만 우회하는 옵션입니다. 스크립트가 하는 일은 화면에 전부 출력됩니다.

스크립트는 세 가지를 합니다. ① 공통 표준 CLAUDE.md를 전역 위치(`~\.claude\CLAUDE.md`)에 설치 — 기존 파일이 있으면 자동 백업합니다(핸드북 1장). ② 사용자 설정에 팀 마켓플레이스와 플러그인을 등록 — 기존 설정은 보존하고 병합만 합니다(핸드북 2장). ③ 필요한 프로그램 확인. 여러 번 실행해도 안전합니다.

**이렇게 되면 성공** — `[OK]` 줄들이 이어지고 완료 안내가 나옵니다. 공통 표준이 제자리에 갔는지 눈으로 확인해봅시다.

```powershell
cat ~\.claude\CLAUDE.md
```

`# CLAUDE.md`로 시작하는 행동 지침이 출력되면 성공입니다. 이 파일이 앞으로 모든 프로젝트에서 Claude가 자동으로 읽는 "일 잘하는 법" 지침서입니다(핸드북 1장).

**만약 `[!!]` 경고와 함께 멈췄다면** — 메시지를 읽어보세요. Claude Code 버전이 낮으면 `claude update`, Node.js가 없으면 STEP 0으로 돌아가면 됩니다.

### STEP 3. 연습 폴더 만들기 + 설치 확인

연습용 빈 폴더를 만들고, 그 안에서 Claude Code를 실행합니다.

```powershell
mkdir C:\work\prod-report
cd C:\work\prod-report
claude
```

Claude Code가 열리면 첫 입력으로 아래를 쳐보세요. 슬래시(`/`)로 시작하는 것은 Claude에게 말을 거는 게 아니라 Claude Code의 메뉴를 여는 명령입니다.

```text
/plugin
```

**이렇게 되면 성공** — 플러그인 목록이 뜨고, 그 안에 `team-guards`와 `team-toolbox`가 활성(enabled) 상태로 보입니다. 이 둘이 앞으로 체험할 안전장치와 진단 도구입니다. 처음에는 플러그인을 내려받느라 잠시 걸릴 수 있습니다.

**만약 안 보인다면** — Claude Code를 껐다가(`/exit`) 같은 폴더에서 다시 실행해보세요. 그래도 없으면 STEP 2의 셋업이 정상 종료됐는지 확인하세요.

> **0부 완료!** 설치는 끝났습니다. 여기서부터는 방금 연 Claude Code 안에서 계속 진행합니다.

## 1부 — 기본 코스 (약 40분, 모든 구성원)

### STEP 4. 프로젝트 준비 — git 저장소 만들기

이제부터는 평범한 한국어로 요청합니다. 아래를 복사해 입력하세요.

```text
새 프로젝트를 시작하려고 해. 이 폴더를 git 저장소로 초기화해줘.
```

git은 "작업 기록장"입니다. 파일의 모든 변경 이력이 남아서, 나중에 뭔가 잘못되어도 이전 시점으로 돌아갈 수 있습니다. 뒤에 나올 저장(커밋)과 진단 기능이 이 기록장을 사용하기 때문에 먼저 만들어 둡니다.

**이렇게 되면 성공** — Claude가 명령 실행 허용을 요청하고(허용해주세요), "git 저장소를 초기화했습니다" 같은 확인을 해줍니다.

### STEP 5. 프로젝트의 기억 만들기 — /init (핸드북 3장)

```text
/init
```

이 명령은 Claude에게 "이 프로젝트를 둘러보고, 다음에 올 너 자신을 위한 안내문을 써둬"라고 시키는 것입니다. 그 안내문이 프로젝트 폴더의 `CLAUDE.md` 파일입니다.

**이렇게 되면 성공** — 폴더에 `CLAUDE.md` 파일이 생깁니다. 지금은 빈 프로젝트라 내용이 몇 줄 안 되는 게 정상입니다. 중요한 것은 이 파일이 **앞으로 작업할수록 자란다**는 점인데, STEP 12에서 실제로 자라는 것을 보게 됩니다.

### STEP 6. 연습용 데이터 만들기

```text
연습용 생산 실적 데이터 production.csv를 만들어줘. 날짜, 라인, 제품, 생산수량, 불량수량
컬럼으로 최근 6개월 치 100행 정도. 라인은 1라인/2라인/3라인 3곳으로.
```

**이렇게 되면 성공** — `production.csv` 파일이 생기고 Claude가 내용 일부를 보여줍니다. 파일 탐색기에서 직접 열어 구경해도 좋습니다.

이 STEP에서 눈여겨볼 것: 데이터 파일을 만드는 것 같은 잔심부름도 그냥 말로 시키면 된다는 것입니다. "엑셀에서 어떻게 만들지"를 고민할 필요가 없습니다.

### STEP 7. 첫 기능 요청 — Claude가 질문하는 모습 관찰 (핸드북 1장)

이제 진짜 기능을 요청합니다.

```text
production.csv를 읽어서 월별 생산량 합계를 표로 출력하는 Node.js 스크립트를 만들어줘.
```

**여기서 볼 것** — Claude가 코드를 바로 쏟아내지 않고 **먼저 물어볼 수 있습니다.** "합계는 생산수량 기준인가요, 불량수량도 함께 보여드릴까요?", "출력은 화면에 표로 보여드리면 되나요?" 같은 질문들이요. 이게 바로 핸드북 1장에서 설치한 공통 지침의 원칙 1 — "추측하지 말고 질문해라" — 이 작동하는 장면입니다. 질문에는 편하게 답하시면 됩니다. 정답이 없으니 "생산수량 기준, 화면 출력이면 충분해" 정도면 됩니다.

**이렇게 되면 성공** — 스크립트 파일이 만들어지고, Claude가 직접 실행해서 월별 생산량 표를 보여줍니다.

**만약 질문 없이 바로 만들었다면** — 그것도 정상입니다. 요청이 충분히 명확하면 Claude는 묻지 않고 진행합니다. 질문은 "애매할 때만" 나옵니다.

### STEP 8. 검증 가능한 목표 주기 (핸드북 1장 원칙 4)

이번에는 요청하는 방식을 살짝 바꿔봅니다. **완료 기준**을 함께 적어주는 것입니다.

```text
라인별 불량률 순위 기능을 추가해줘.
완료 기준: 스크립트를 실행하면 월별 생산량 합계와 라인별 불량률 순위가 모두 출력되고,
실행 중 오류가 없어야 해.
```

**여기서 볼 것** — Claude가 기능을 만든 뒤 **완료 기준을 스스로 검증하고** 끝냅니다. "실행해서 두 표가 모두 나오는 것을 확인했습니다"처럼요. 완료 기준이 없으면 "다 된 것 같아요"를 받게 되고, 있으면 "확인했어요"를 받게 됩니다. 이 차이가 쌓이면 재작업이 크게 줄어듭니다.

이 요령은 오늘 이후 **모든 실전 요청에** 쓸 수 있습니다. 요청 끝에 "완료 기준: ~" 한 줄을 붙이는 습관, 강력히 추천합니다.

### STEP 9. 안전장치 구경 ① — 위험 명령 차단 (핸드북 2장)

이번엔 일부러 위험한 요청을 해봅니다. 안전장치가 막아줄 것이므로 실제로는 아무 일도 일어나지 않습니다.

```text
git reset --hard 실행해줘
```

이 명령은 "저장 안 한 작업을 전부 버리고 마지막 저장 시점으로 되돌려라"라는 뜻으로, 실수로 실행되면 작업물이 날아가는 대표적인 위험 명령입니다.

**이렇게 되면 성공** — 실행되는 대신 이런 차단 메시지가 나타납니다.

```text
Dangerous Command Guard
git reset --hard는 작업 중인 변경사항을 되돌릴 수 있습니다.
차단된 명령: git reset --hard
이 작업이 정말 필요하면 사용자가 명령을 직접 검토한 뒤 수동으로 실행하세요.
```

그리고 Claude가 차단 사유를 읽고 "이 명령은 위험해서 차단되었습니다. 정말 필요하시면..." 하고 대안을 설명해줍니다. **이 메시지의 생김새를 기억해두세요.** 실전에서 만나면 "고장났다"가 아니라 "안전장치가 일했다"입니다. 대응법은 핸드북 2장에 있습니다.

### STEP 10. 안전장치 구경 ② — 공통 표준 보호 (핸드북 2장)

하나 더 구경해봅니다.

```text
전역 CLAUDE.md 파일에 "항상 반말로 대답해줘"를 추가해줘
```

**이렇게 되면 성공** — 이것도 차단됩니다. 전역 CLAUDE.md(`~\.claude\CLAUDE.md`, STEP 2에서 설치한 그 파일)는 모두가 함께 쓰는 공통 표준이라, Claude를 시켜서 고치는 것이 막혀 있습니다. 프로젝트 폴더 안의 CLAUDE.md(STEP 5에서 만든 것)는 자유롭게 관리할 수 있고요.

개인 취향 지침을 정말 추가하고 싶다면 메모장으로 그 파일을 직접 열어 맨 아래에 적으면 됩니다 — 사람이 직접 하는 것은 막지 않습니다(핸드북 1장 FAQ 참고).

### STEP 11. 작업 저장 — 커밋

여기까지 만든 것을 기록장(git)에 저장합니다.

```text
지금까지 작업을 커밋해줘. 커밋 메시지는 알아서 정리해줘.
```

**이렇게 되면 성공** — Claude가 어떤 파일들이 바뀌었는지 확인하고, 요약 메시지를 붙여 저장합니다. 이제 이후에 무슨 실수가 있어도 이 시점의 상태는 안전하게 남아 있습니다. 실전에서도 "의미 있는 작업 단위 하나가 끝나면 커밋"을 습관으로 하시면 좋습니다.

### STEP 12. 오늘 배운 것 저장 — /revise-claude-md (핸드북 3장)

**이 코스에서 가장 중요한 습관이 나옵니다.** 작업 세션을 마무리할 때 아래 한 줄을 입력하는 것입니다.

```text
/revise-claude-md
```

**이렇게 진행됩니다** — Claude가 이번 세션을 돌아보며 "다음에 알았으면 좋았을 것들"(이 프로젝트의 실행 명령, 데이터 파일 구조, 결정 사항 등)을 찾아서 CLAUDE.md에 추가하자고 제안합니다. 제안을 훑어보고 승인하세요.

**이렇게 되면 성공** — 승인 후 `CLAUDE.md` 파일을 열어보면(또는 "CLAUDE.md 보여줘"라고 하면) STEP 5 때보다 내용이 자라 있습니다.

**왜 중요한가** — 오늘 Claude가 알아낸 것을 기록하지 않으면, 다음 세션의 Claude는 처음부터 다시 알아내야 합니다. 기록하면 다음부터는 즉시 압니다. 이 한 줄을 세션 마칠 때마다 입력하는 것만으로 Claude가 프로젝트를 점점 더 잘 아는 동료가 되어갑니다.

### STEP 13. 프로젝트 진단 — AI-Ready 점수 (핸드북 4장)

내 프로젝트가 Claude가 일하기 좋은 상태인지 채점을 받아봅니다.

```text
이 레포 AI-readiness 점수 매겨줘
```

**이렇게 진행됩니다** — Claude가 채점 도구를 돌리고(1~2분), 브라우저에 대시보드가 열립니다. 100점 만점 점수, 등급, 영역별 점수, 그리고 "개선 액션 리스트"가 보입니다.

**점수가 낮아도 놀라지 마세요.** 방금 시작한 프로젝트라 문서가 거의 없으니 낮은 게 당연합니다. 이 점수는 성적표가 아니라 "어디부터 고치면 효과가 큰지" 알려주는 지도입니다. 이어서 개선을 시켜봅니다.

```text
개선 액션 리스트에서 효과가 가장 큰 것 하나를 적용해줘
```

적용이 끝나면 한 번 더:

```text
다시 점수 매겨줘. 아까보다 올랐는지 알려줘.
```

**여기서 볼 것** — 점수가 오릅니다. **진단 → 개선 → 재진단.** 이 사이클이 이 도구 사용법의 전부이고, 실전에서는 "Claude가 이 프로젝트에서 유독 헤맨다" 싶을 때 돌리면 됩니다.

**만약 "Python이 필요합니다" 오류가 나면** — 채점 도구가 Python이라는 프로그램을 사용합니다. Claude가 설치 방법을 안내해줄 테니 따라 하시고, 어려우면 팀에 문의하세요.

### STEP 14. 비용 확인 — 토큰 효율 (핸드북 5장)

Claude Code는 쓰는 만큼 비용이 나가는 도구입니다. 내가 어떻게 쓰고 있는지 확인해봅니다.

```text
토큰 효율 분석해줘
```

**이렇게 되면 성공** — 이 프로젝트에서 지금까지 쓴 비용, 효율 점수, 개선 제안이 대시보드로 나옵니다. 오늘 처음 시작해서 데이터가 적으니 숫자 자체보다 **도구가 있다는 것**을 알아두는 게 목적입니다. 한 달쯤 쓴 뒤에 다시 돌려보면 진짜 유용해집니다.

마지막으로, 비용 절약에 가장 효과가 큰 명령을 체험해봅니다.

```text
/compact
```

**이렇게 되면 성공** — 지금까지의 긴 대화 이력이 요약본으로 압축됩니다(잠깐 시간이 걸립니다). 대화 이력은 매번 처리 비용에 포함되기 때문에, **큰 작업 하나가 끝날 때마다 이걸 입력**하면 이후 비용이 크게 줄어듭니다. 원리가 궁금하면 핸드북 5장을 보세요.

> **1부 완료!** 일상 사용에 필요한 것은 전부 체험하셨습니다. 오늘 가져갈 습관 딱 두 개만 기억하세요:
> **세션을 마칠 때 `/revise-claude-md`, 큰 작업이 끝나면 `/compact`.**

## 2부 — 심화 코스 (약 30분, 개발 작업이 많은 분, 선택)

2부는 코드를 자주 만드는 분을 위한 코스입니다. "테스트가 먼저인 개발(TDD)"과 "스펙이 먼저인 개발(SDD)"을 체험합니다. 1부를 마친 같은 폴더에서 이어서 진행하세요.

### STEP 15. TDD Guard 켜기 (핸드북 6장)

TDD Guard는 기본으로 꺼져 있는 선택 장치입니다. 이 연습 프로젝트에서만 켜봅니다.

```text
이 프로젝트의 .claude/settings.json에 team-dev-practice@company-tools 플러그인을
켜는 설정을 추가해줘
```

설정 파일이 만들어지면, **Claude Code를 종료했다가(`/exit` 입력 또는 창 닫기) 같은 폴더에서 다시 실행**하세요. 플러그인은 시작할 때 읽히기 때문에 재시작이 필요합니다.

**재시작 후 확인** — `/plugin`을 입력해서 `team-dev-practice`가 활성 상태인지 확인하세요.

### STEP 16. TDD 흐름 체험 — 차단에서 통과까지 (핸드북 6장)

이 STEP이 2부의 하이라이트입니다. 재시작한 세션에서 새 기능을 요청합니다.

```text
불량률을 계산해서 등급을 판정하는 기능을 quality.js 파일로 추가해줘.
불량률이 2% 미만이면 "양호", 5% 이상이면 "점검 필요", 그 사이면 "주의"야.
```

**이렇게 진행됩니다 (지켜보세요):**

1. Claude가 `quality.js`를 만들려는 순간 **TDD Guard에 차단**됩니다 — "테스트 파일이 존재하지 않습니다. 테스트를 먼저 작성하세요."
2. Claude가 차단 사유를 읽고, **스스로 테스트부터** 만듭니다. "불량률 1%면 양호가 나오는가", "불량률 7%면 점검 필요가 나오는가" 같은 검사 항목들이요. 테스트 실행 도구가 없으면 그 설치까지 알아서 합니다(허용 창이 몇 번 뜰 수 있습니다).
3. 테스트가 생겼으니 이제 구현이 허용됩니다. 구현을 만들고, **테스트를 실행해 전부 통과하는 것을 확인**한 뒤 완료를 보고합니다.

**여기서 볼 것** — 여러분은 평소와 똑같이 한 문장으로 요청했을 뿐인데, 결과물에 "통과한 테스트"라는 증거가 따라왔습니다. 이게 TDD Guard를 켜고 일하는 방식의 전부입니다. 경계값이 궁금하면 이렇게 물어보세요.

```text
불량률이 정확히 5%면 어떤 등급이야? 테스트로 확인해줘.
```

### STEP 17. 커밋 검증 체험 — Pre-commit Check (핸드북 2장)

개발 실천 가드에는 커밋 문지기도 포함되어 있습니다.

```text
품질 판정 기능 커밋해줘
```

**여기서 볼 것** — 커밋되기 직전에 자동 검사(테스트 등)가 돌아가는 로그가 보이고, **전부 통과해야만** 커밋이 완료됩니다. 만약 어딘가 고장난 상태였다면 커밋이 차단되고 Claude가 먼저 고칩니다. 고장난 코드가 저장소에 들어가는 일을 원천 차단하는 장치입니다.

### STEP 18. SDD 맛보기 — 큰 작업의 시작법 (핸드북 7장)

지금까지는 기능 하나씩 요청했지만, 만약 이 도구를 "라인별 대시보드 + 월간 리포트 자동 발송 + 이상 생산 감지까지 갖춘 시스템"으로 키운다면 어떨까요? 그렇게 크고 모호한 작업을 한 문장으로 시작하면, 며칠 뒤 "내가 원한 것과 다른 물건"이 나오기 쉽습니다. 그래서 큰 작업은 **스펙 합의부터** 시작합니다.

```text
이 프로젝트에 SDD 세팅해줘
```

**이렇게 되면 성공** — `docs/` 폴더에 스펙 문서 골격 4개(PRD, ARCHITECTURE, ADR, UI 가이드)와 실행 도구가 생깁니다. 이어서 스펙 작성을 체험해봅니다. 직접 쓰는 게 아니라 **Claude의 질문에 답하는 방식**입니다.

```text
docs/PRD.md를 채우고 싶어. 나한테 질문하면서 초안을 같이 만들어줘.
목표는 "생산 실적 리포트 자동화 도구"야.
```

**여기서 볼 것** — Claude가 "주 사용자는 누구인가요?", "가장 중요한 기능 셋을 꼽는다면?" 하고 인터뷰하듯 물어보며 초안을 완성해갑니다. 여러분의 역할은 쓰는 것이 아니라 **답하고 승인하는 것**입니다.

실제 대형 작업에서는 이 다음에 `/harness`(스펙을 작은 단계들로 분해)와 자동 실행이 이어지는데, 오늘은 여기까지만 하겠습니다. 전체 흐름과 "언제 SDD를 쓰고 언제 안 쓰는지" 판단 기준은 핸드북 7장에 있습니다.

### STEP 19. 마무리

심화 코스에서 배운 것까지 프로젝트의 기억에 저장하고 마칩니다.

```text
/revise-claude-md
```
